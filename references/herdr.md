# Herdr 관측 pane (선택)

Herdr 안에서 Claude Code 리드를 돌릴 때, 작업자(Grok, Sol, Sonnet 등)마다 별도 pane에 실시간 상태를 보여 준다. Herdr 밖(CLI, VS Code 등)에서는 아무것도 하지 않고 이전과 같다.

## 켜고 끄는 법

`HYPERFUSION_HERDR`는 세 상태다.

| 값 | 동작 |
|---|---|
| 없음(기본) | 자동 감지. Herdr pane 안(`HERDR_PANE_ID`가 있음)이면 켜고, 밖이면 조용히 건너뛴다. 기록도 남기지 않는다. |
| `0` | 항상 끈다. Herdr 안에서도 pane을 열지 않는다. |
| `1` | 강제로 켠다. Herdr 밖이면 열 수 없으므로 건너뛰되, 이유를 작업자의 activity 로그에 남긴다. |

그 밖의 값은 켜지 않는다. 켜진 경우에도 첫 pane을 열기 전에 `herdr pane get`으로 현재 pane이 살아 있는지 확인한다. 환경 변수만 물려받았고 Herdr는 이미 닫혔거나 서버에 닿지 않으면 pane을 만들지 않고 건너뛴 이유를 남긴다.

pane 안 셸에 명령 문자열을 보내므로 셸 종류에 맞는 따옴표 규칙을 쓴다.

| 환경 | 처리 |
|---|---|
| Linux, macOS, WSL | POSIX 셸로 보고 작은따옴표로 인용한다. |
| Windows 네이티브 | `herdr pane process-info`로 새 pane의 셸을 확인한다. PowerShell(`pwsh`, `powershell`)은 `& '경로' ...`, `cmd.exe`는 큰따옴표로 인용한다. `%`나 `"`가 든 경로는 cmd에서 안전하게 인용할 수 없어 건너뛴다. |
| 그 밖의 셸 | 알 수 없는 셸이면 만든 pane을 닫고 건너뛴다. |

`herdr` 실행 파일은 `HYPERFUSION_HERDR_BIN`, 없으면 pane이 넣어 주는 `HERDR_BIN_PATH`, 그것도 없으면 PATH의 `herdr`를 쓴다.

## 무엇을 하나

- 브리지가 작업자를 원래대로 헤드리스로 띄운 직후, 관측 pane에서 `herdr pane run`으로 `scripts/herdr-observer.mjs view <작업 폴더> <tag> <컨트롤러 PID>`를 실행한다.
- pane 배치:
  - 앞서 쓴 관측 pane 중 셸 프롬프트에서 쉬고 있는 것(전면 프로세스가 셸뿐)이 있으면 그 자리에 새 화면을 띄운다.
  - 없으면 마지막 관측 pane 아래로 새 pane을 쌓고, 관측 pane이 하나도 없으면 리드 pane 오른쪽에 만든다.
  - 그래서 라운드가 늘어도 리드 pane은 한 번만 나뉘고, pane 수는 동시에 도는 작업자 수를 넘지 않는다. 사용자가 무언가 실행 중인 pane은 다시 쓰지 않는다.
- 브리지는 라운드마다 새 프로세스이므로, 리드 pane마다 관측 pane 목록을 `<상태 폴더>/herdr/<해시>.json`에 남긴다. 상태 폴더는 `HF_STATE_DIR`, 기본은 `~/.hyperfusion/state`다. 이 기록은 편의일 뿐이라 쓸 때마다 Herdr에 pane이 살아 있는지 다시 확인하고, 읽지 못하면 새로 나눈다.
- 화면은 그 작업자의 `monitor-<tag>.json`과 `activity-<tag>.ndjson` 끝 8줄을 읽어 1초마다 갱신한다. 줄은 pane 폭에 맞게 자르고 끝에 `…`를 붙여, 좁은 pane에서도 줄이 접히지 않는다. 한글·한자 등 전각 문자는 두 칸으로 센다.
  - 프로세스 종료가 관측되면 마지막 화면을 남기고 끝난다.
  - 컨트롤러 프로세스가 최종 상태를 쓰지 못하고 사라져도 그 사실을 표시하고 멈춘다. pane은 닫지 않는다.
- 작업자 출력에서 온 문자열은 터미널 제어 문자(C0·C1, 양방향 텍스트 제어)를 `?`로 바꿔 표시한다. 그래서 작업자가 ESC 시퀀스로 화면 제목·클립보드·링크를 조작할 수 없다.
- 어느 pane이 붙었는지(또는 왜 건너뛰었는지)는 해당 작업자의 activity 로그에 `diagnostic`으로 남는다.
- HyperFusion 자체 시험(`npm test`, `tests/support.mjs`)은 `HYPERFUSION_HERDR=0`으로 돌아서, Herdr 안에서 시험해도 pane을 열지 않는다.

## 바뀌지 않는 것

- 작업자 프로세스의 소유자, PID·프로세스 그룹 기록, 종료 증명, stdout JSON 검증, 결과 digest는 모두 컨트롤러 그대로다. Herdr는 프로세스를 소유하지 않는다.
- pane 화면은 읽기 전용 관측이다. `EXITED`나 `idle`은 수용 테스트 통과나 성공 판정이 아니다.
- Herdr 호출이 실패하거나 느려도 라운드의 성공·실패와 writer lease는 달라지지 않는다. 호출 하나는 5초, pane 하나를 붙이는 전체 과정은 10초가 상한이다. 브리지는 종료 증명 전에 이 과정을 기다리므로 Herdr가 응답하지 않아도 라운드 마무리가 그 이상 늦어지지 않는다.
- 명령 문자열의 경로와 태그는 작은따옴표로 인용하고, 태그는 `[\w-]+`만 받는다. Herdr가 돌려준 pane id도 형식을 검사한 뒤 쓴다.

## 수용 검사와의 관계

관측 pane은 일꾼 라운드 중에 만들어지고, 그 셸과 `view` 프로세스는 Herdr 서버의 자식이라 일꾼의 자손이 아니다. 수용 검사는 명령마다 시작 직전의 프로세스 목록을 기준으로 저장하므로, 라운드 중에 만든 pane은 그 목록에 들어 있다. Windows Herdr에서 일꾼 라운드 중 pane을 만든 뒤 수용 검사를 돌리고, 검사 도중 pane을 직접 하나 더 열어도 정지 증명을 통과하는 것을 확인했다.

단 Herdr 서버를 수용 검사 도중에 처음 띄우면(서버를 띄운 셸이 먼저 끝나 부모 없는 프로세스가 남는 경우) `ACCEPTANCE_NOT_QUIESCENT`로 멈춘다. 관측 pane 때문이 아니라 검사 도중 새로 생긴 프로세스 전반에 해당하는 규칙이므로, Herdr를 먼저 띄운 뒤 그 안에서 실행한다.

## 아직 하지 않는 것

작업자 자체를 Herdr의 `agent start`로 띄우는 실행 백엔드는 구현하지 않았다. 프로세스 소유권, 종료 증명, 중복 실행 방지, 재개 정산을 새로 설계해야 하는 별도 과제다.
